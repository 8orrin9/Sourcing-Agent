# LLM 계층 — 분류·병합·RFI 회신

작성일: 2026-11-07
상위: [아키텍처_261107.md](아키텍처_261107.md)
대상: `src/llm/client.py`, `src/llm/classify.py`, `src/llm/merge.py`, `src/llm/rfi.py`

## 요약

수집 계층(앵커·확산 추출기)이 뱉은 원시 `SupplierRecord`를 **판단 가능한 정보**로
끌어올리는 LLM 계층을 구현했다. 세 가지 결정적 문제를 구조화 출력(structured output)으로 푼다:

1. **분류·역량 판정**(classify) — 이 후보가 실제 제조사인가? 요청 공정(HC/AF)을 보유하는가?
2. **엔티티 병합**(merge) — 웹검색 후보와 팩토리온 앵커가 같은 회사인가?
3. **RFI 회신 왕복**(rfi) — 정보 요청 회신을 생성하고, 그 회신으로 증거 등급을 승급.

모든 호출은 `complete_json`을 거쳐 JSON Schema strict 모드로 받으므로, 반환값은
스키마를 만족하는 dict로 신뢰할 수 있다(파싱 실패·형식 붕괴 없음).

## 1. 클라이언트 격리 (`client.py`)

다운스트림은 `complete_json(system, user, schema, ...)` 하나에만 의존한다. 모델·
프로바이더 교체는 이 모듈만 고치면 된다.

- `DEFAULT_MODEL = gpt-4o-mini` (환경변수 `SOURCING_LLM_MODEL`로 override). 비용·속도 균형.
- 구조화 출력: `response_format={"type":"json_schema", ..., "strict":True}`.
- 결정성: `temperature=0.0`.

### 사내망 TLS — truststore 재귀 회피 (실측 교정)

`pip-system-certs`(httpx 직접 호출용 Windows 인증서 신뢰)가 `ssl.verify_mode`를
몽키패치하는데, openai SDK가 쓰는 `truststore`와 **둘 다 Windows 저장소를 신뢰**하려다
`RecursionError`로 무한 재귀했다.

→ 해결: openai 클라이언트에 **명시적 `httpx.Client(verify=ssl.create_default_context())`**
를 주입. 독립 SSL 컨텍스트라 truststore 경로를 타지 않는다. `get_client()`은
`@lru_cache`로 프로세스당 1회만 생성.

## 2. 분류·역량 판정 (`classify.py`)

확산 소스(웹검색)는 특허·학회·블로그·디렉터리 노이즈가 많고, 팩토리온 주생산품은
자유어라 키워드 매칭이 안 된다. 두 문제를 LLM이 동시에 처리한다.

- 출력: `is_manufacturer`(bool) + `kind_reason` + `capabilities[]`(code·evidence·basis).
- `PROCESS_DEFS = {HC, AF, LASER}` — enum으로 스키마에 박아 환각 코드를 원천 차단.
- 보수적 판정: 출처 도메인이 `patents.*`·`*.or.kr`(학회)·`blog.*`·`news`이거나 회사명이
  서술적 문서 제목이면 제조사 아님. **애매하면 `is_manufacturer=false`.**
- 증거 수준 L1(웹 언급)/L2(설비·사양·사진)/L3(인증·시험성적서·납품실적). 근거 없으면 공정 미포함.
- 결과는 `model_copy`로 원본 불변. 앵커가 넣은 capability 우선 유지 후 추가, `[LLM] reason` 노트 누적.

실증: 서진코팅 → manufacturer·HC L2·AF L2. 특허문서/학회자료 → trader(프롬프트 강화 후).

## 3. 엔티티 병합 (`merge.py`)

웹검색은 회사명·URL만, 팩토리온 앵커는 주소·공장·생산품을 준다. 같은 회사의 조각을
합쳐야 하는데 **사업자번호가 없고**(팩토리온 미제공) 회사명 표기 변형이 심하다
('서진코팅' / '(주)서진코팅' / '서진코팅(주)'). 규칙 매칭은 취약 → LLM 판정.

- `is_same_company(a, b)` → `{same_company, confidence(high/medium/low), reason}`.
- 병합 방향: **앵커(검증됨)가 base**, 확산 후보를 흡착. 결과 `verified=True` 유지 + 확산 출처도 provenances 누적.
- `merge_into`: base 우선, 빈 필드만 채우고 products·capabilities·provenances·notes는 누적(순수 로직, 테스트 커버).
- `absorb_candidates`: **1차로 정규화 회사명(`_norm_name`)이 포함관계인 앵커만** LLM에 물어
  호출 수를 줄인다(비용 절감). `min_confidence` 이상만 병합. (병합 앵커들, 잔여 후보) 반환.

실증: "서진코팅"(web) → "(주)서진코팅"(anchor) 흡착, domain 채움, provenance 2건, verified=True.

## 4. RFI 회신 왕복 (`rfi.py`)

숏리스트 업체에 RFI(정보 요청)를 보내 회신의 인증서·시험성적서로 증거 등급을
승급하는 흐름. 실제 메일 발송은 시연 불가라 **회신을 LLM으로 3분기 생성 → 다시 파싱**
하는 왕복을 실연한다.

- `SCENARIOS = (full, partial, none)` — 데모 RFI_REPLY 3분기(완전/부분/무응답) 계승.
  full→인증서·시험성적서 첨부, partial→설비 사양만, none→`responded=false`.
- `generate_reply(rec, requested_processes, scenario)` → `{responded, body, attachments}`.
- `parse_reply(reply, requested_processes)` → 승급 항목 `[{code, new_evidence, basis}]`. 무응답이면 빈 리스트.
- `apply_upgrades(rec, upgrades)` → **상향만** 반영(L1→L3 O, L2→L1 무시). 알 수 없는 코드 무시.
  원본 복제 수정, `[RFI 승급]` 노트 누적.

### 존 분리 (엄수)

RFI 본문·회신에 **내부 단가·내부 품목코드·현 협력사명을 넣지 않는다.** 요구 정보는
소싱 스펙의 공정 정의에서만 생성. 생성 프롬프트에도 명시.

실증: full→L3, partial→L2, none→승급 없음. 3분기 모두 동작.
