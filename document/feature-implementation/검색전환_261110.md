# 후보 탐색 전환 — 스펙 기반 검색 계획 · 공장등록 우선 발견 · 웹 LLM 회사 추출

작성일: 2026-11-10
대상: `src/` 백엔드, `html/Demo_Sourcing-Agent_261110.html`

## 왜 바꿨나

이전 흐름은 사람이 쓴 고정 검색어 5개로 웹 검색을 하고, 검색결과 **제목 앞부분을 회사명**으로
써서 팩토리온·KIPRIS에 조회했다. 실제 SerpApi 응답(KR) 7건은 모두 특허·학회·판매 페이지였고,
그 '회사명'으로 공공DB를 조회하니 대부분 0건이었다. 노이즈는 맨 뒤 LLM 분류에서야 걸러졌다.

구매 담당자가 원하는 후보는 "뻔하지 않으면서 믿을 수 있는 곳"이다. 그래서 다음 세 가지를 바꿨다.

1. **스펙 → 검색어를 자동으로, 역할을 나눠서 만든다** (STEP 0)
2. **발견을 공장등록에서 시작한다** — 공장이 있는 제조사가 모집단, 웹은 보조·상세 수집용
3. **웹 검색 결과는 검색 직후 LLM이 실제 기업만 추출한다** — 제목 자르기 폐지

## 1. STEP 0 — 자연어 + 사양서 → 스펙 → 검색 계획

- `src/core/documents.py` `read_document`: 사양서 PDF 텍스트 추출(pypdf). 스캔 PDF는 미지원(OCR 범위 밖).
- `src/llm/spec_parse.py` `parse_spec`: 요청문 + 사양서 → 6개 그룹 항목, 필수/우대 제안, 근거(사양서 항 번호),
  사양 수치 → 공정 매핑("연필경도 3H → 하드코팅"). **공정 항목마다 소스별 검색어**를 같이 만든다.
  - 공장등록 생산품란용 짧은 품목 명사 / 특허 키워드 + IPC / 웹 로케일별 검색어
  - 레이저 커팅 같은 **범용 가공은 검색어를 만들지 않는다**(무관 업체가 쏟아짐) — 검증 항목으로만 남는다.
  - 내부 품목코드는 LLM 프롬프트에 넣지 않는다.
- `to_ui_spec` / `apply_selection`: 화면 JSON(그룹별 required/preferred)과 상호 변환. 담당자가 필수/우대를
  바꿔도 LLM을 다시 부르지 않는다.
- `src/search_plan.py` `build_search_plan` (결정적):

| 역할 | 스펙 항목 | 쓰는 곳 |
| --- | --- | --- |
| 발견 | **필수 핵심 공정**의 검색어 + 품목 일반어 | 공장등록 생산품 검색, KIPRIS 기술검색, 웹 검색 |
| 게이트 | 필수 지역·규모·제외 | 신뢰 게이트(탈락) |
| 검증 | 공정·설비·인증 전체 | 상세 수집 후 LLM 스펙 체크 → 점수 |
| 가점 | 우대 항목, 근접 지역 | 점수 가점 |

  웹 로케일은 지역 항목에서 정한다(국내→KR, 베트남→VI, 해외가 있으면 EN). 내부 품목코드·금지어(현 협력사명)가
  들어간 검색어는 여기서 결정적으로 제거하고 `removed`에 남긴다.

예시 출력 형식: `data/synthetic/parsed_spec_pmma.json` (손으로 작성한 시연값 — 라이브 LLM 출력으로 교체 가능).

## 2. 발견 소스 전환 (`src/pipeline.py`)

```
① 공장등록 생산품 검색   FactorionExtractor.search(product=…)  → 공장 중복 제거 → 회사 단위(종업원 합산·최초 등록연도)
② 특허 기술검색          KiprisExtractor.search_tech(word, ipc) → 기업 출원인(대학·연구기관·개인 제외)
                         → 공장등록 회사명 조회로 확인된 곳만 후보
③ 웹 검색(보조)          WebSearchExtractor.search → llm/company_extract.extract_companies(기업만)
                         → 국내는 공장등록 대조, 해외는 미확인 유지
→ merge_pool → 신뢰 게이트(pre_gate: 지역·최소 종업원·유통사, 모르는 값은 통과)
→ LLM 관련성 1차 선별(screen_candidates: '하드코팅 강판' 같은 동음이의 제거, 25건 배치)
→ 상위 N(공장등록 > 특허 > 종업원 순): 특허 보강 → 홈페이지 확정 → 크롤·PDF → 스펙 체크 → 점수 → 숏리스트
```

- 회사명 대조(`merge.resolve_to_factory`): 정규화명이 같으면 규칙으로, 포함관계면 LLM 동일회사 판정.
- KIPRIS 출원인명 조회는 부분일치라 다른 회사 특허가 섞이던 문제를 고쳤다(출원인명이 정확히 같은 특허만 집계).
- 모든 외부 호출은 실패해도 그 건만 건너뛰고 `log`에 남긴다. 결과에 단계별 `log`·`excluded`(탈락 사유) 포함.

## 3. 상세 수집 (`src/extractors/site_detail.py`)

- 홈페이지: 공장등록 값 → 없으면 웹 검색 결과에서 LLM이 공식 사이트 판별(`pick_homepage`, 마켓·채용·뉴스 제외).
- `crawl`: 같은 도메인 링크를 키워드(회사·설비·인증·제품…)로 우선순위 → 최대 8쪽, PDF(카탈로그·인증서·소개서)
  최대 3건 다운로드·텍스트 추출. 문서는 페이지보다 앞에 둬서 길이 상한에 잘리지 않게 했다. 실패 URL은 건너뛴다.
- `Fetcher.get_bytes`: PDF용 바이너리 다운로드(캐시·robots·재시도·10MB 상한).

## 4. 판정·점수

- `llm/classify.py` `classify_supplier`: 코드에 박혀 있던 HC/AF/LASER 목록을 없애고 **스펙 항목 자체**를 판정 단위로
  쓴다(met/partial/unmet/unknown + L1~L3 + 근거). 품목이 바뀌어도 코드 수정이 필요 없다. 공장등록 레코드는
  LLM이 유통사로 봐도 제조사로 유지한다(공적 기록 우선).
- `llm/score.py` 배점(합 100): 필수 공정 35 · 필수 설비 10 · 필수 인증 10 · 신뢰 25(공장등록 10 · 종업원 기준 8 ·
  업력 10년+ 4 · 특허 3) · 지역 10 · 우대 10. 게이트: 유통사 · 허용 지역 밖 · 종업원 확인값 미달 · 필수 공정 근거 0.
  근접 지역은 시도 동일/인접으로 근사한다(지오코딩 없음).

## 5. 데모 반영 (`html/Demo_Sourcing-Agent_261110.html`, 261107은 보존)

- STEP 0: 파싱 단계 표시, 사양 → 공정 매핑 표시, **검색 계획(역할 분리) 카드** — 필수/우대 토글 시 즉시 재계산
  (`build_search_plan`의 JS 이식, 항목별 검색어는 `parsed_spec_pmma.json`과 동일).
- STEP 1: 공장등록 우선 소스·실행 로그(공장등록 → 특허 → 웹 AI 추출 → 병합 → 신뢰 게이트·관련성 선별), 게이트 제외 표시.
  스펙의 허용 지역(국내·베트남)에 맞춰 중국 업체 예시를 베트남으로 옮겼고, 청우코텍 인원을 게이트 기준 이상으로 조정.
- 증거 콘솔: 새 채점 체계로 재계산한 값(`scripts/regen_evidence.py`)과 축별 점수 구성 표시.
- STEP 2: 홈페이지 판별(공장등록 공란 → 웹 + AI), 링크 우선순위, PDF 다운로드·텍스트 추출 로그.
