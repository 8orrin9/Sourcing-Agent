## 0. 전체 비즈니스 맥락 — 왜 이 에이전트인가

삼성디스플레이 구매팀의 재협상·대체 소싱에서 가장 비싼 병목은 **"대체 공급원을 찾는
리서치"**다. 담당자가 구글·전시회·지인망으로 후보를 찾고, 하나씩 홈페이지·특허·공장
등록을 뒤져 "진짜 제조사인지, 요구 공정을 가졌는지"를 손으로 검증한다. 품목 하나에
수 주가 들고, 결과의 재현성·감사 추적성이 없다.

이 에이전트의 비즈니스 명제는 **"구글링을 넘는 리서치를 자동화하되, 담당자가 신뢰하고
감사에 쓸 수 있는 형태로 산출한다"**이다. 그래서 세 기능은 각각 다음을 책임진다.

| 기능 | 담당자의 수작업 | 에이전트가 대체하는 것 |
| --- | --- | --- |
| ① 후보 탐색 | 구글·디렉터리·공장등록·특허를 따로따로 검색 | 다국어·다소스 통합 조회 + 공공데이터 교차검증 |
| ② 상세 수집 | 후보 홈페이지를 일일이 열람 | robots 준수 크롤 + 근거·출처 자동 기록 |
| ③ 숏리스트 | 엑셀로 주관적 점수 매김 | 규칙 기반 설명가능 점수 + 노이즈 자동 제거 |

**관통하는 설계 원칙 2가지** (모든 기능이 공유):

- **존 분리(Zone Separation)**: 외부 수집(후보 탐색)과 내부 분석(단가·현 협력사 비교)을
  물리적으로 가른다. 외부로 나가는 쿼리·RFI에는 내부 단가·품목코드·현 협력사명이
  **절대** 들어가지 않는다. → 영업비밀 유출·협상 패 노출 방지라는 구매 부서의 1순위
  리스크를 구조로 차단.
- **증거 우선(Provenance-first)**: 모든 판정 값은 "어느 소스가, 어떤 추출기로, 무엇을
  근거로" 만들었는지 추적된다. → 숏리스트는 감사·내부 품의의 근거 자료가 되어야 하므로,
  "왜 이 업체인가"에 항상 답할 수 있어야 한다.

## ① 후보 업체 탐색 (롱리스트)

### 무엇을 하는가
소싱 스펙(공정·소재 키워드)으로 다국어 웹·B2B 디렉터리·공장등록·특허를 **동시 조회**해
공급사 후보 목록(롱리스트)을 만들고, 공공데이터로 **교차검증**한다.

### 왜 이렇게 설계했는가 (비즈니스 → 설계 결정)

**결정 1. "앵커 / 확산" 2원 구조.**
현실의 소스는 두 종류다. 웹검색·디렉터리는 **재현율은 높지만**(많이 찾음) 회사명·URL만
주어 "이게 진짜 그 회사인지" 식별이 약하다. 반대로 공장등록(팩토리온)·특허(KIPRIS)는
**정밀하지만**(주소·공장번호·사업자 단위) 그걸로 신규 발견은 안 된다. 그래서:
- **확산(SPREAD)** 소스 = 넓게 긁는 그물 → `verified=False`
- **앵커(ANCHOR)** 소스 = 식별을 확정하는 기준점 → `verified=True`
- 확산이 찾은 회사명을 앵커에 넣어 **흡착(검증)**한다.

→ 비즈니스 효과: "구글에서 본 이름"을 "공공DB로 실재가 확인된 제조사"로 승격시키는
과정을 자동화. 담당자가 가장 못 믿는 "검색 결과의 신뢰도" 문제를 정면으로 푼다.

**결정 2. 비용순 계층(Cost-ordered Registry).**
소스를 붙이는 비용이 제각각이다(공공 API는 싸고 안정적, LLM 추출은 비쌈). 무작정 다
돌리면 비용·시간이 폭발한다. 그래서 싼 계층부터 시도하고, 필요할 때만 비싼 계층으로
폴백하는 우선순위를 둔다.

→ 비즈니스 효과: "사이트 pool을 자생적으로 넓힌다"는 확장성을, 운영비를 통제하면서
달성. 신규 사이트 편입 비용이 (YAML 한 장 / 설정 0)으로 떨어진다.

**결정 3. 존 분리를 입력단에서 강제.**
검색 쿼리는 스펙의 `search_queries`(공정·소재 키워드만)에서만 생성하고, 내부
`mat_code`·`incumbent`는 스키마상 외부 함수로 전달되지 않는다.

### 어떻게 동작하는가 — 구현 방법론

**단일 계약 (`src/schema.py`)**
모든 추출기는 출처가 무엇이든 `SupplierRecord` 하나로 정규화해 출력한다. 다운스트림
(병합·점수·숏리스트)은 "어느 계층이 만들었는지" 모른다 → 소스 교체·추가가 다운스트림에
무영향. `SourceClass`(ANCHOR/SPREAD)·`Provenance`(출처 추적)·`EvidenceLevel`(L1/L2/L3)을
enum으로 고정.

**레지스트리 (`src/extractors/registry.py`, `base.py`)**
추상 베이스 `Extractor`가 `tier·source_id·source_class`를 선언하고 `extract(query)`를
구현하도록 강제. `Registry.register()`가 `tier` 오름차순으로 정렬 보관 →
`for_source()`가 "싼 계층부터" 돌려준다. 각 추출기 모듈은 **import 시 자기 자신을
전역 레지스트리에 등록**(사이드이펙트 등록 패턴) → 사용부는 import만 하면 계층이 자동 구성.

라이브 확인된 계층:
```
tier1 factorion (anchor)   — 공장등록 OpenAPI, 주소·공장번호 → verified=True
tier1 kipris    (anchor)   — 특허 출원인 OpenAPI, 기술분야 근거 → verified=False(준앵커)
tier2 web_search(spread)   — Serper 다국어 검색(KR/EN/ZH/VI)
tier2 ec21 / gobizkorea    — YAML 셀렉터 디렉터리
tier4 llm_extract(spread)  — 안티봇 사이트 LLM 폴백
```

**각 계층의 구현 기법**
- **1계층 팩토리온** (`structured.py`): 공공데이터포털 XML을 `ElementTree`로 파싱. 회사명
  부분일치(`cmpnyNm`) 조회만 지원하므로 "발견"이 아니라 **확산이 찾은 이름을 검증**하는
  앵커로 씀. 주소·공장관리번호 확보 → `verified=True`. 홈페이지 필드에 주소 조각 등
  쓰레기가 섞여 들어오므로 `_looks_like_url`로 URL 형태일 때만 채택(방어적 파싱).
- **1계층 KIPRIS** (`kipris.py`): 특허 서지 OpenAPI를 출원인명으로 조회. 한 출원인의
  특허 다건을 **1개 레코드로 집계**(출원인=기업). 주소를 안 주므로 `verified=False`인
  **준앵커** — "특허 보유 + 기술분야(발명명칭·IPC)"를 역량 근거로만 보탠다. 매칭 실패는
  감점이 아니라 "근거 없음".
- **2계층 웹검색** (`web_search.py`): Serper(Google) API. `LOCALE` 테이블로 한·영·중·베
  `gl/hl` 파라미터 전환. Alibaba·made-in-china 등 `AGGREGATOR_DOMAINS`는 제조사 자체
  사이트가 아니므로 홈페이지로 안 쓰고 회사명만 추출. 라이브 호출과 픽스처가 같은
  `_parse`를 공유(키 없이도 로직 테스트 가능).
- **2계층 디렉터리** (`config_driven.py`): B2B 디렉터리는 CSS 셀렉터를 **YAML로 선언**.
  `config/*.yaml` 한 장 추가 → import 시 자동 등록. `BeautifulSoup`로 `item_selector`
  블록을 자르고 `fields`의 셀렉터·attr로 값 추출. **코드 수정 없이 사이트 확장**.
- **4계층 LLM 폴백** (`llm_extract.py`): 설정·코드 없는 사이트를 커버. HTML에서
  script/style/head를 제거하고 앵커 텍스트 옆에 URL을 심어(`<href>`) 12,000자로 축약 →
  LLM structured output으로 회사 목록 추출. 가장 비싸므로 tier=4(최후 폴백).

**흐름** (`pipeline.py::discover` → `anchor_merge`)
```
discover(spec)          스펙 다국어 쿼리로 웹검색을 로케일별 실행(한 쿼리 실패는 삼킴)
   │                    → 회사명·URL 중심 확산 롱리스트
   ▼
anchor_merge(candidates)
   ├ 팩토리온 verify(회사명들)  → 앵커 레코드(verified=True)
   ├ dedupe_factories()        → 한 기업의 여러 공장 레코드를 회사명 기준 1건으로 접음
   └ absorb_candidates()       → 확산 후보를 앵커에 LLM 흡착(verified 승격)
                               → (검증된 앵커들, 흡착 못한 잔여 후보) 둘 다 숏리스트 후보
```
- **엔티티 병합** (`merge.py`): 사업자번호 같은 결정적 키가 없고 회사명 표기 변형
  ('서진코팅' vs '(주)서진코팅')이 많아, "같은 회사인가"를 **LLM으로 판정**. 비용 절감을
  위해 1차로 정규화 회사명(`_norm_name`: 법인격·공백 제거)이 겹치는 앵커만 LLM에 질의.
  `confidence ≥ medium`일 때만 병합.
- **공장 중복 접기** (`dedupe_factories`): 팩토리온은 한 기업의 사업장을 각각 등록 →
  같은 회사가 주소만 다른 여러 건으로 나온다. 정규화 회사명이 같으면 결정적으로(LLM 없이)
  1건으로 접고 `[사업장 N개 통합]` 표식.
- **특허 근거 보강** (`enrich_patents`): KIPRIS는 새 후보를 만들지 않고, 회사명이 일치하는
  기존 레코드에 특허 제목·IPC·provenance를 `merge_into`로 누적만 한다(준앵커 원칙).

### 동작 검증 (라이브)

## ② 업체 상세 수집

### 무엇을 하는가
롱리스트 업체의 웹사이트(회사·설비·인증·제품 페이지)를 열어 상세 프로필을 수집하되,
**robots.txt를 지키고 근거·출처를 함께 기록**한다. 두 계층으로 구성된다: 수집을 떠받치는
**공통 인프라(Fetcher)** + 사이트 구조에 의존하지 않고 상세를 뽑는 **상세 추출기**.

### 왜 이렇게 설계했는가

**결정 1. "사이트 무관 공통 계층"으로 분리.**
수백 개 후보 사이트는 제각각이지만, 그들을 긁는 **공통 관심사**(캐시·레이트리밋·robots·
재시도·TLS)는 똑같다. 이를 사이트별 로직과 섞으면 추출기마다 중복·실수가 생긴다. 그래서
`Fetcher` 한 객체가 공통 관심사를 전담하고, 추출기들은 이를 공유한다.

→ 비즈니스 효과: ① **법적 안전**(robots 준수 — 외부 크롤의 ToS/법무 리스크 차단),
② **시연 안정성**(캐시로 동일 URL 재요청을 디스크에서 즉답 → 데모가 네트워크에 안 흔들림),
③ **사내망 대응**(자체 서명 CA로 HTTPS를 가로채는 사내 환경을 env로 흡수).

**결정 2. 캐시 = 골든 픽스처 주입 경로 겸용.**
같은 캐시 경로에 저장된 실HTML을 넣으면 오프라인에서도 동일 코드가 돈다 → 안티봇 사이트도
스냅샷으로 재생. 개발·테스트·시연이 모두 같은 코드 경로를 쓴다.

**결정 3. "사이트마다 다른 구조"는 CSS 셀렉터가 아니라 LLM으로 흡수.**
업체 홈페이지는 구조가 제각각이다(현대적 div/section · 구식 table 레이아웃 · 프레임 등).
사이트마다 셀렉터를 손으로 짜면 수백 개 후보를 감당할 수 없고, 사이트가 개편되면 바로
깨진다. 그래서 상세 추출은 **HTML 구조가 아니라 '의미'로 읽는 LLM 추출**을 쓴다(①의
4계층 `llm_extract` 방법론을 '발견'이 아니라 '상세'에 맞춰 재사용).

→ 비즈니스 효과: 신규 업체 사이트를 **설정·코드 없이 즉시 수집**. "구조가 특이해서 이
업체는 못 본다"는 사각지대를 없앤다 — 후보 pool 자생 확장의 상세 단계 버전.

### 어떻게 동작하는가 — 구현 방법론

**(a) 공통 인프라 (`src/core/fetcher.py`)**
- **디스크 캐시**: URL을 sha256으로 해싱해 `data/cache/<key>.html`. `get()`은 캐시 우선,
  최종 요청 URL(params 반영) 기준으로 키를 잡음.
- **robots.txt**: `urllib.robotparser`로 origin별 1회 로드·캐시. 못 읽으면 보수적 허용.
  `can_fetch(UA, url)`로 차단 판정 → 차단 시 `PermissionError`.
- **rate-limit**: `time.monotonic()` 기반 스로틀(기본 요청 간 1초).
- **retry**: `tenacity`로 전송오류·HTTP오류에 지수 백오프(1→10초) 최대 3회.
- **사내망 TLS**: `SOURCING_CA_BUNDLE`(CA 경로) / `SOURCING_SSL_VERIFY`(검증 on/off)
  env로 `httpx.Client`의 verify를 제어.
- 2계층·4계층 추출기가 이 **한 Fetcher를 공유**(지연 생성 property).

**(b) 상세 추출기 (`src/extractors/site_detail.py`, tier=4)**
- `query={'urls': [...]}`(라이브) 또는 `{'html', 'url'}`(픽스처). urls를 주면 Fetcher로
  회사·설비·인증·제품 페이지를 받아 **이어붙인 뒤 한 번에 판정**(토큰 상한 16,000자 절단).
- `_clean`: script/style/head 제거, 앵커 텍스트 옆에 URL을 심음(`<href>`) → 구조 태그를
  버리고 '의미 텍스트'만 남김. **이 단계가 "구조 무관성"의 핵심** — table이든 div든 같은
  평문 흐름으로 환원된다.
- LLM structured output으로 고정 스키마 추출: 회사명·국가·지역·주소·제조사여부·임직원·
  **설비 배열·인증 배열**·제품·담당부서·대표연락처·요약. 스키마 strict라 반환값 신뢰 가능.
- 결과를 `SupplierRecord`에 매핑: 설비·인증은 `notes`에 `[설비]`/`[인증]` 접두로 남겨
  LLM 공정 역량 판정(③ classify)과 점수의 '규모 단서'가 쓰도록 함.
- **개인정보 비저장**: 스키마가 담당 '부서'와 대표 이메일/전화만 받고, 개인 이름 필드는
  아예 없음(프롬프트에서도 금지). **존 분리**: 업체 자체 주장이므로 `verified=False`
  (앵커 흡착·RFI 회신으로만 승격).

### 동작 검증 (라이브)
공통 인프라: 수집 OK · **캐시 동작**(1회차 0.22s → 2회차 0.009s) · **robots 판정 동작**

상세 추출기 — **구조가 완전히 다른 두 사이트를 같은 추출기로 처리**(핵심):

## ③ 숏리스트 선정

### 무엇을 하는가
수집된 후보에서 **노이즈(제조사 아님)를 걸러내고**, 소싱 스펙 적합도를 **설명가능한
점수**로 매겨 상위 N개사를 선정한다.

### 왜 이렇게 설계했는가

**결정 1. 점수는 LLM이 아니라 "결정적 규칙"으로.**
숏리스트는 내부 품의·감사의 근거가 된다. LLM이 "82점"이라고만 하면 "왜 82점인가"에
답할 수 없고 재현도 안 된다(같은 입력에 다른 점수). 그래서 **점수 산술은 명시 규칙으로
고정**하고, 항목별 가점 사유(`breakdown`)를 함께 낸다. LLM이 만든 것은 역량·업종 판정
(`capabilities`·`kind`)뿐이고, 그걸 스펙과 대조하는 계산은 결정적.

→ 비즈니스 효과: **설명가능성·재현성·감사 대응**. "이 업체가 왜 1위인가"를 축별로
제시(공정역량 45 중 몇 점, 왜) → HITL(담당자 확정) 의사결정을 뒷받침.

**결정 2. "게이트"로 하드 제외.**
유통·무역사, 요청 공정 0개 업체는 아무리 다른 점이 좋아도 숏리스트 부적격 — 점수와
별개로 `passed_gate=False`. 구매팀의 "제조사만, 공정 보유 필수"라는 비타협 조건을 명시.

**결정 3. 노이즈 제거는 LLM 분류가 전담.**
웹검색은 특허문서·학회·뉴스·블로그를 대량으로 끌고 온다(①에서 라이브로 확인됨). 이를
키워드로 거르면 취약하다. LLM이 "이 주체가 실제 제조 기업인가"를 판정해 `trader`로 찍어
게이트에서 떨군다.

### 어떻게 동작하는가 — 구현 방법론

**(a) LLM 분류 (`src/llm/classify.py`)**
- structured output(JSON Schema strict)으로 `is_manufacturer` + `capabilities`
  (code·evidence L1/L2/L3·basis)를 받음 → 스키마 미준수 시 SDK가 거부하므로 반환값 신뢰 가능.
- 시스템 프롬프트가 "특허문서·학회·뉴스·연구기관·디렉터리·유통사는 is_manufacturer=false,
  애매하면 보수적으로 false"로 노이즈 기준을 명시. 근거 없는 역량은 넣지 말라고 강제.
- 입력은 회사명·생산품·소재지·출처·스니펫(=수집 근거)만 — 추측 금지.

**(b) 규칙 스코어링 (`src/llm/score.py`)**
```
배점(합 100): capability 45 · manufacturer 20 · verified 15 · region 12 · scale 8
 - capability : 요청 공정별 증거수준(L1=1·L2=2·L3=3) 합 / 최대치 × 45
 - manufacturer: 제조사면 20 (유통사 0)
 - verified   : 앵커 교차검증(provenance.verified)되면 15
 - region     : 국내 또는 선호지역 매칭이면 12
 - scale      : notes에 종업원 등 규모 단서 있으면 8
게이트: kind==TRADER 또는 요청 공정 0개 → passed_gate=False
```
각 축마다 `{axis, points, max, reason}`을 반환 → 완전 설명가능. 존 분리: 내부 단가·현
협력사 비교는 여기 없다(숏리스트가 내부망에 들어간 뒤 수행).

**흐름 (`pipeline.py`)**
```
classify_all(enriched)  각 레코드 LLM 판정 → kind·capabilities 채움(노이즈=trader)
   ▼
score_all(records, spec) 스펙 공정·선호지역으로 점수+breakdown 산출
   ▼
shortlist(scored, top_n) passed_gate만 추려 점수 내림차순 → 상위 N
   ▼
_result_row()           외부 공개 필드만 평탄화(존 분리) → 데모가 읽을 JSON
```

### 왜 "부분 구현"인가
판정 두뇌(분류·점수·게이트)는 **완성**이다. 다만 ① 점수 입력인 `capabilities`를 채우는
전처리가 LLM 판정 1회 의존(데모 funnel의 DART·국세청·국민연금 교차검증 깊이까지는 안 감),
② 데모의 "필수조건·가중치 슬라이더 실시간 재계산" UI 연동이 백엔드에 없어 현재는 정적
결과 주입. → **엔진은 동작, 대화형 재계산 연결이 미완.**

### 동작 검증 (라이브)
- 스코어링: 만점 사례(제조사·HC/AF L3·검증·국내·규모 = 100) breakdown 전 축 정확,
  유통사 27점·게이트 탈락, 공정0개 47점·탈락, 미검증 해외 제조사 58점·통과.
- 분류: "…하드코팅 필름 제조방법"(특허) → trader, "서진코팅"(제조사) → manufacturer,
  "한국광학필름협회" → trader. **노이즈 제거 정확.**
