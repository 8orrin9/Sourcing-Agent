# Second Chair 소싱 에이전트 — 업무 확장 설계서

작성일: 2026-11-01
상위 문서: [STEP_0_구현설계서_261025.md](STEP_0_구현설계서_261025.md)

## 왜 확장하는가

현장(IPC·소싱 담당) 피드백 결과, 기존 PoC는 소싱 라이프사이클의 **가운데 토막(발견 → 검증 → 분석)** 만 다루고 있었습니다. 실제 IPC 업무는 그 **앞(요청 접수)·중간(RFI 컨택)·뒤(사후 실행 추적)** 가 모두 붙어야 하나의 일로 완성됩니다. 이 문서는 그 세 단계를 신설하고, 전체를 담을 UI 골격을 재정의합니다.

> **설계 원칙은 그대로 계승합니다.** 증거 우선 · 에이전트/코드 분업 · 존 분리 · 사람 확인 지점. 신설 단계도 이 네 원칙 위에서 설계합니다.

## 재정의된 라이프사이클

기존 6단계(STEP 0~5)를 **5개 업무 국면(phase)** 으로 재편하고, 신설 3단계를 끼워 넣습니다.

```
【접수】            【발견·검증 — 현행】                  【컨택 — 신설】      【분석 — 현행】     【실행 — 신설】
소싱 요청       →   STEP0 스펙 → 1 롱리스트            →  RFI 발송·회신·분석  →  STEP4 연계분석   →  견적·방문·테스트
(STEP_6-1)          → 2 상세수집 → 3 숏리스트              (STEP_6-2)            → STEP5 브리프      (STEP_6-3)
```

| 국면 | 포함 단계 | 신규/현행 | 존 |
| --- | --- | --- | --- |
| 접수 | 소싱 요청 창구 | **신설** | 내부 |
| 발견·검증 | STEP 0~3 (스펙·롱리스트·상세·숏리스트) | 현행 | 외부 |
| 컨택 | RFI 발송·회신·분석 | **신설** | 외부(발송)/경계 |
| 분석 | STEP 4~5 (연계분석·브리프) | 현행 | 내부 |
| 실행 | 소싱 실행 추적(견적·방문·테스트·등록) | **신설** | 내부 |

핵심은 **흐름이 끊기지 않는다**는 것입니다. 요청이 들어오면 → 발견·검증을 거쳐 → 업체에 실제로 RFI를 보내고 회신을 관리하며 → 내부 분석으로 협상 근거를 만들고 → 소싱 이후 등록까지 가는 긴 과정을 한 화면에서 추적합니다.

## 신설 단계 요약 (상세는 각 문서 참조)

### 접수 — 소싱 요청 창구
구매현황 자동 진단(에이전트 제안형)에 더해, **담당자 수동 요청형**(선행연구·신제품)을 신설합니다. 산업군/기술 + **품목·자재코드 검색·지정** + **유사 자재 추천**. 요청자(수요부서)가 올리고 IPC가 받아 소싱 파이프라인으로 넘깁니다.

> 트리거 이원화, 요청 폼 필드, 자재코드 검색·유사 자재 추천 로직은 [STEP_6-1_소싱요청_261101.md](STEP_6-1_소싱요청_261101.md) 참조.

### 컨택 — RFI 발송·회신·분석
숏리스트 업체에 실제로 접촉합니다. 컨택 포인트 발굴 → **RFx 자동 작성** → 발송·추적 → **무응답 자동 조치** → **회신 자동 분석**(증거 등급 승급). RFI는 이후 확정 스펙으로 RFP로 발전합니다.

> 컨택 포인트 추출, RFx 템플릿, 무응답 에스컬레이션, 회신→증거등급 승급 로직은 [STEP_6-2_RFI컨택_261101.md](STEP_6-2_RFI컨택_261101.md) 참조.

### 실행 — 소싱 실행 추적
소싱 확정 후 "즉시 대체 불가"라는 현실을 반영해, **견적 → 방문 → 테스트 → 승인·등록** 파이프라인을 업체별 타임라인으로 추적합니다.

> 실행 스테이지 정의, 업체별 타임라인/칸반, 지연 알림은 [STEP_6-3_실행모니터링_261101.md](STEP_6-3_실행모니터링_261101.md) 참조.

## UI 골격 재정의

좌측 레일 → **상단 가로 GNB**로 전면 전환하고, GNB 아래에 **프로세스 진행 현황 스텝퍼**를 상시 노출합니다. **요청자/IPC 역할 전환**을 도입합니다.

> GNB 메뉴 트리, 스텝퍼, 역할 전환, 팔레트 적용(블랙·화이트·블루·하늘색) 상세는 [STEP_6-4_UI골격_261101.md](STEP_6-4_UI골격_261101.md) 참조.

## 데이터 모델 확장

기존 모델(STEP_0 데이터 모델)에 신설 단계용 엔티티를 추가합니다. 모든 신규 사실도 Evidence로 원문 역추적이 가능해야 합니다.

| 엔티티 | 주요 필드 | 연결 |
| --- | --- | --- |
| SourcingRequest | 요청 ID, 요청자, 수요부서, 트리거(자동/수동), 산업군, 품목명, 자재코드, 사양 요약, 상태 | 모든 단계의 루트 키 |
| MaterialRef | 자재코드, 품목명, 사양, 현 협력사, 단가 이력, 임베딩 | 유사 자재 추천의 대상 |
| ContactPoint | Supplier 참조, 이메일, 부서, 출처 URL, 수집일 | STEP 2 크롤링에서 함께 추출 |
| RfxRequest | RFI/RFP 번호, 대상 Supplier 목록, 발송일, 마감일, 상태 | SourcingRequest에 귀속 |
| RfxResponse | RfxRequest 참조, 회신일, 첨부, 파싱 결과, 증거 승급 로그 | Capability 등급 승급에 연결 |
| ExecutionStage | SourcingRequest 참조, 스테이지(견적/방문/테스트/등록), 상태, 예정일, 담당자 | 사후 추적 타임라인 |
| Role | 사용자, 역할(요청자/IPC/열람), 권한 | 역할 전환·접근 제어 |

## 범위와 트레이드오프 (PoC 기준)

- **골격 전부 + 핵심만 동작.** 신설 3단계는 화면·흐름을 모두 만들되, 실제 동작은 각 단계 핵심 1~2기능에 집중하고 나머지는 자리만 확보합니다(데모 무게 관리).
- **외부 발송의 현실.** RFI 실제 메일 발송은 PoC 범위 밖(STEP_0 "범위 밖: 실제 RFQ 발송"과 정합). 데모에서는 발송·회신·추적을 **시뮬레이션**으로 보여주고, 실발송은 2차 과제로 명시합니다.
- **역할 전환 비용.** 요청자/IPC 스위칭은 설득력을 높이지만 상태관리가 늘어납니다. PoC는 역할별 "보이는 화면/액션"만 구분하고 권한 서버 검증은 생략합니다.

## 신설 단계와 기존 원칙의 접점

| 신설 요소 | 기존 자산과의 연결 |
| --- | --- |
| 자재코드·유사 자재 추천 | 품목 마스터(MaterialRef) + pgvector(기존 기술스택) |
| 컨택 포인트 | STEP 2 크롤링 파이프라인에 추출 항목 추가(개인정보 비저장 원칙 준수: 부서·대표 연락처 위주) |
| RFI 회신 분석 | 증거 등급 L1~L3 체계에 그대로 접속 — "주장만" → "서류 확인"으로 승급 |
| 실행 추적 | 숏리스트/브리프의 산출물을 이어받아 상태만 전진 |
